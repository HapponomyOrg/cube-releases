Troubleshooting

No. 028

Find your message on this page: search for a few of its words with your browser’s find (Ctrl+F) or with this site’s search. Each entry shows the message as the program prints it. A part in angle brackets, such as <version>, stands for a value on your machine.

Run cube doctor in your knowledge base’s folder first. It checks git, Python, the hooks, risky git settings and the kit’s tools, and says what to fix.

If your message is not here, read the FAQ and the known limits, then report the problem.

The installers

Section titled “The installers”

The installers print install.sh: (Linux and macOS) or install.ps1: (Windows) before each line. After an error, the installer removes what it downloaded and installs nothing. The version you had stays.

minisign is not installed

Section titled “minisign is not installed”

This is not an error. The installer goes on, and it still checks GitHub’s record of the release and the SHA-256 of the download. To check the signature too, install the minisign program and run the installer again. On Windows, minisign.exe must be on your PATH. See what the installer checks.

The manifest expired

Section titled “The manifest expired”

Each channel manifest is valid for 90 days, and it is signed again every month (When releases come). So first check the date and time of your computer: the installer compares the expiry with them. If they are right, report the problem. An installed cube keeps working.

GitHub’s record cannot be read

Section titled “GitHub’s record cannot be read”

The installer could not reach GitHub’s API. The usual causes:

  • You are offline, or a proxy is in the way (see behind a proxy).
  • GitHub answered HTTP 403 or 429: GitHub allows 60 anonymous API calls an hour from one address. Wait an hour and try again.

To install anyway, set CUBE_INSTALL_SKIP_GITHUB_CHECK=1. Then only this site’s manifest vouches for the file. See when GitHub’s API cannot be reached.

A download fails

Section titled “A download fails”

Check that you are online and that your machine can reach happonomyorg.github.io and github.com. Behind a proxy, see the next entry.

Behind a proxy

Section titled “Behind a proxy”

The installers set no proxy of their own. They use the proxy settings of the programs that download:

  • Linux and macOS: curl and wget read the https_proxy variable (curl also reads HTTPS_PROXY). Set it before you run the installer:

  • Windows: PowerShell uses the proxy that Windows is set to use (Settings, Network and internet, Proxy). PowerShell 7 reads the HTTPS_PROXY variable first, when it is set.

The same settings apply to all three downloads: the manifest, the archive and GitHub’s record of the release.

The signature does not match

Section titled “The signature does not match”

The manifest is not the one that Happonomy signed. Do not install around this check. Try again later. If the message stays, report it privately: see Security.

A checksum does not match

Section titled “A checksum does not match”

A download was cut short or changed on the way. Run the installer again. If the message stays, report it privately: see Security.

The installer is older than the manifest

Section titled “The installer is older than the manifest”

Your copy of the installer is older than the manifest. Run the install command again: it downloads the newest installer. If you saved a copy of the script, download it again.

The installer refuses sudo

Section titled “The installer refuses sudo”

Run the install command as yourself, without sudo. The installer installs for your own account only (see where it installs).

No build for this system

Section titled “No build for this system”

The Cube has builds for these systems only. See requirements.

This release has no build for your system

Section titled “This release has no build for your system”

On Windows:

The Cube publishes a release when its Linux tests pass. If the macOS or Windows build fails, the release has no build for that system, and its release notes say so. The installer installed nothing. You can choose one of two things:

  • Wait for a release that has a build for your system, and run the installer again then.
  • Run the command that the installer printed. It installs the older release, and checks it as it checks every release: the signature, GitHub’s record and the SHA-256. The older release gets no fixes. Up to 0.2.0 it has no cube self update, so run the installer again later, without CUBE_VERSION, to get a newer release.

The installer never installs the older release by itself. If the manifest names no earlier release with a build for your system, the installer says so.

If cube is installed already, cube self update says that the release has no build for your system and changes nothing. Your cube keeps working.

The installer for another system

Section titled “The installer for another system”

Run the command that the message names.

A program the installer needs is missing

Section titled “A program the installer needs is missing”

Install the program from your system’s packages, then run the installer again. See the installers and the uninstallers.

The downloaded program does not run

Section titled “The downloaded program does not run”

On Windows, the usual cause is Smart App Control. With Smart App Control on, Windows runs no unsigned program, and the programs of The Cube are not code-signed. See code signing. On Linux and macOS, report the problem with the output of uname -a.

cube is not found after the install

Section titled “cube is not found after the install”

Add the line that the installer prints to your shell’s startup file, then open a new terminal. On Windows, the installer adds %LOCALAPPDATA%\Programs\cube\current to your user PATH; a terminal that was open before the install does not see it, so open a new one.

cube

Section titled “cube”

Python cannot be used

Section titled “Python cannot be used”

The kit’s own checks need Python 3.10 or later with PyYAML 6 (requirements). On Linux and macOS, install Python 3, or put the folder that holds python3 on your PATH as an absolute path. A relative folder in PATH, such as ., does not count. If the git hooks are on, run cube setup again afterwards: it records the path of python3 for the hooks. On Windows, cube looks up no python3: run cube setup --python <path to python.exe> or cube setup --venv <folder> in the knowledge base. cube doctor shows the interpreter that cube setup recorded in its python item.

PyYAML or NetworkX is not installed

Section titled “PyYAML or NetworkX is not installed”

These are python-library items of cube doctor. Install PyYAML 6 for the interpreter that cube doctor names: the starter kit’s checks need it. The starter kit and the architecture pack do not use NetworkX. From 0.3.0, cube doctor judges only the libraries that the kit’s runtime.python.packages lists, so with the starter kit it says that NetworkX is not needed; 0.2.0 still reported it as missing and exited 3. cube check and the hooks do not need it.

The kit’s checks are skipped

Section titled “The kit’s checks are skipped”

cube check runs the engine’s own checks and skips the kit’s on a system that has no form of the check that a program is safe to run. Linux, macOS and Windows have one from 0.4.0. A cube of 0.3.0 skips the kit’s checks on macOS and Windows: upgrade (Upgrade).

cube setup or cube doctor refuses on macOS and Windows

Section titled “cube setup or cube doctor refuses on macOS and Windows”

These are messages of 0.3.0. From 0.4.0, cube setup and cube doctor work on macOS and Windows: run the installer once to upgrade (Upgrade).

cube setup refuses the Microsoft Store’s python

Section titled “cube setup refuses the Microsoft Store’s python”

On Windows, the python.exe in %LOCALAPPDATA%\Microsoft\WindowsApps is not Python but a link to the Store. Install Python, then give cube setup --python the path of its own python.exe, or give cube setup --venv the folder of a venv.

cube setup warns that the hooks will refuse a program

Section titled “cube setup warns that the hooks will refuse a program”

The installer puts cube in your home folder, and the hooks run only a program that root owns, unless you opt it in. Whether to opt in is your decision; cube never writes the opt-in itself. To opt in, run the git config command that the message prints. Read the programs the hooks run first.

Every hook warns that it is not tamper-proof

Section titled “Every hook warns that it is not tamper-proof”

This is expected after the opt-in. An agent that runs as your account can change a program that your account owns, and the hooks cannot see that. An install that root owns, which closes this gap, comes in a later release.

cube setup did not run through the command link

Section titled “cube setup did not run through the command link”

Run cube setup through the cube command that the installer linked (for example ~/.local/bin/cube setup), or run the installer again to make the link.

A command is not built yet

Section titled “A command is not built yet”

The command name is kept for a later release, and cube exits 3. See not in this release.

The agent skill is stale

Section titled “The agent skill is stale”

The agent skill in your knowledge base was written by another cube or for another kit.yml. Write it again with cube skill render --install, and commit it. See the quick start.

write refused: not adopted

Section titled “write refused: not adopted”

The knowledge base has no .cube/cube.toml. Run cube adopt first. See the quick start.

write refused: a newer format or a newer cube

Section titled “write refused: a newer format or a newer cube”

A cube of 0.3.0 on macOS and Windows says run the installer again in place of cube self update:

A newer cube wrote this knowledge base, or the knowledge base asks for one. This cube still reads it, but it writes nothing. Upgrade The Cube with cube self update, or, from 0.3.0 on macOS and Windows, with the installer (Upgrade). See versioning and compatibility.

The kit needs a newer cube

Section titled “The kit needs a newer cube”

A cube of 0.3.0 on macOS and Windows says run the installer again in place of cube self update:

The kit is newer than this cube, so cube does not load it. Upgrade The Cube with cube self update, or, from 0.3.0 on macOS and Windows, with the installer (Upgrade). See versioning and compatibility.

cube self update and the update check

Section titled “cube self update and the update check”

cube self update and cube self rollback print cube self update: or cube self rollback: before a refusal, and exit 3. After a refusal, the version you had stays current; most refusals end with nothing was changed. Where an entry quotes cube self update:, cube self rollback: can print the same.

cube self refuses on macOS and Windows

Section titled “cube self refuses on macOS and Windows”

This is a message of 0.3.0, whose cube self update and cube self rollback work only on Linux. They exit 3 and fetch nothing. From 0.4.0 they work on macOS and Windows too: run the install command once to upgrade (Upgrade).

The install belongs to another account

Section titled “The install belongs to another account”

cube self update changes only the install that the installer made for your own account. An install that root or another account owns is updated by that account, not by yours.

This cube is not in the installer’s folders

Section titled “This cube is not in the installer’s folders”

This cube was copied by hand, for example for an install without a network, or it runs without the command link that the installer made. Run the install command once (Upgrade); after that, cube self update keeps the install up to date. See where it installs.

The manifest is refused

Section titled “The manifest is refused”
  • Expired: each channel manifest is valid for 90 days, and it is signed again every month (When releases come). First check the date and time of your computer. If they are right, report the problem. The installed cube keeps working.
  • The signature, the key or the serial: the manifest is not one that Happonomy signed, or it is older than one that this account saw before. Do not update around this check. Try again later. If the message stays, report it privately: see Security.

GitHub’s record or the checksum does not match

Section titled “GitHub’s record or the checksum does not match”

When GitHub answers HTTP 403 or 429, the first message adds (GitHub allows 60 anonymous requests an hour per address; try again later): wait an hour and try again. Otherwise check that you can reach api.github.com (see the network). A digest or a checksum that does not match means that a download was cut short or changed on the way: try again. If the message stays, report it privately: see Security.

A download fails

Section titled “A download fails”

Check that you are online and that your machine can reach happonomyorg.github.io, api.github.com and github.com. cube self update reads a proxy only from ALL_PROXY, HTTPS_PROXY, HTTP_PROXY and NO_PROXY, and it judges certificates with your system’s certificate store. See the network.

tar is not found

Section titled “tar is not found”

Install tar, or add its folder to your PATH as an absolute path. Like the programs that the hooks run, tar must be owned by root or by your account (see requirements).

The cache folder is not used

Section titled “The cache folder is not used”

cube self update keeps the serials of the manifests it saw in your cache folder (~/.cache/cube, or $XDG_CACHE_HOME/cube). The folder must belong to your account, must not be a link, and must have mode 0700. The part in brackets says what is wrong. For a wrong mode, run:

Nothing to roll back to

Section titled “Nothing to roll back to”

cube self rollback goes back only to a kept version that is older than the current one. After a rollback, the version you left is kept, and cube self update returns to it.

The manifest expires soon

Section titled “The manifest expires soon”

The explorer shows this under its title bar, and cube doctor adds it to its update-check item as a warning:

The warning starts 21 days before the last manifest that cube verified expires. Happonomy signs the manifest again every month, and the next daily check then finds the new expiry date and the warning goes away. First check the date and time of your computer. If the warning stays for more than a few days, report the problem. The installed cube keeps working. See privacy for the update check.

The git hooks

Section titled “The git hooks”

A hook prints cube hook <name>: before its message, and git stops the commit, merge or push. From 0.4.0, the hooks run on Linux, macOS and Windows.

A commit is refused

Section titled “A commit is refused”

The commit adds an ERROR. The fix brief is also saved in .cube/cache/fix-brief.md in your knowledge base. The fix brief above the line says, for each ERROR, its rule, a real fix, what is not a fix and the act that the fix needs. cube check --format agent prints it again. See what the hooks refuse.

A program is not safe to run

Section titled “A program is not safe to run”

The hooks run only programs that root owns, or programs in your home folder that you opted in. See cube setup warns that the hooks will refuse a program.

The hooks refuse on macOS and Windows

Section titled “The hooks refuse on macOS and Windows”

This is the refusal of 0.3.0, whose hooks refuse every commit on macOS and Windows. Upgrade to 0.5.1 (Upgrade), then run cube setup in the knowledge base. Until then, to turn the hooks off in a clone, run this in it:

Git for Windows is missing

Section titled “Git for Windows is missing”

On Windows, the hooks and cube doctor read protected git config only with Git for Windows’ own git.exe under Program Files, never with a per-user Git install. Install Git for Windows for every account (the installer’s default), then commit again. See the known limits.

A setting of cube setup is missing

Section titled “A setting of cube setup is missing”

Run cube setup in the knowledge base. If python3 was missing when you ran it, install Python 3 first (see Python cannot be used).

On Windows, the hook shims that an earlier cube wrote into .cube/hooks/ print the first message too when they find no git: Git for Windows 2.56 moved its git.exe from mingw64\bin to ucrt64\bin, where they do not look. cube setup does not change the shims. Run cube adopt once in the knowledge base, which writes the shims again and commits them, then cube setup.

The knowledge base is not the top level of its repository

Section titled “The knowledge base is not the top level of its repository”

In 0.5.1, the hooks and cube setup work only for a knowledge base at the top level of its own git repository.

The format is unknown to this cube

Section titled “The format is unknown to this cube”

A newer cube wrote this knowledge base. Upgrade The Cube on this machine (Upgrade). See write refused: a newer format or a newer cube.

A human-only act passes unsigned

Section titled “A human-only act passes unsigned”

This is a warning, not a refusal. Signed acts are opt-in, and this knowledge base has not opted in: no trust root is pinned, and the commit’s first parent holds no .cube/allowed_signers. So a rule change, the clearing of a bypass and a change to the code that judges commits pass without a signature. pre-push, the bypass scan, commit-msg and pre-commit all say so, each with the hint once. To make such acts count only when you sign them, run cube trust init (see signed acts).

cube trust init: the adoption commit is on no remote yet

Section titled “cube trust init: the adoption commit is on no remote yet”

Push, then run cube trust init again. cube trust init also refuses, before it changes anything, outside a git repository and when the index holds staged changes (commit them, or unstage them with git reset --quiet). Making a new key needs a terminal, where ssh-keygen asks for the passphrase: run it in a terminal, or give your public key with --key FILE.

No trust root is pinned

Section titled “No trust root is pinned”

<act> names the act, for example it changes the code that judges commits (_kit/tools/check.py): a human-only act. The knowledge base asks for signed acts, because the commit’s first parent holds .cube/allowed_signers, but no trust root is pinned on this machine. So no signature counts, and pre-push refuses every act that needs one, also a signed one. pre-commit’s bypass scan lists the same. This is what a teammate sees after another person started signing: one person’s cube trust init opts in the whole knowledge base.

Run cube trust init to join the knowledge base’s signers. It shows the commit that opted in and the fingerprint of the key that signed it. Compare the fingerprint with the person who started signing, by chat or in person, then type its last 8 characters. It pins that commit, sets up signing in your clone, and prints a line with your key: send it to a trusted signer, who adds it in a signed commit (see Teams). Your signed acts count after you pull that commit; when the file lists your key already, they count at once. If you made the commit that opted in yourself, compare with your own key’s fingerprint. When root pinned that commit in the system config, cube trust init asks for no fingerprint. You can also pin the trust root by hand, as signed acts shows. When a pin is there but does not count, the part after but says why instead, and ends with so no signature counts; the owner pins it and the guide:

Set both values again, in the same config, as pin the trust root shows: cube.trustRoot is the full commit id of the signed commit that added .cube/allowed_signers, and cube.trustKey is the fingerprint of the key that signed it. Fetch first, so that your clone has that commit.

cube trust init: joining needs a person at a terminal

Section titled “cube trust init: joining needs a person at a terminal”

Run cube trust init yourself, in a terminal, without --yes. It also refuses without a terminal. Both apply only while you must type the fingerprint: once your own pin, or root’s pin in the system config, names the commit that opted in, --yes works. When what you type is not the last 8 characters of the fingerprint, it stops at step 2 and changes nothing.

Before it changes anything, it also refuses to join in these cases. Then nobody can join from this history: ask the person who started signing.

The first says that a key that its own copy lists did not sign the commit that added .cube/allowed_signers. The second names a later commit that changed .cube/allowed_signers or .cube/revoked_signers without a signature by a key listed before it, as pre-push would refuse it: for example an agent that added its own key, or a removal and a copy added again.

The commit that opts in is not signed

Section titled “The commit that opts in is not signed”

In every knowledge base, the commit that adds .cube/allowed_signers counts only when a key that its own copy lists signed it, so that no AI agent can opt a knowledge base in with a list that names its own key. In place of it is not signed, the line can say that a key the copy does not list signed it. The commit is not on the remote yet. Take it back: when it is your last commit, git reset HEAD~1 keeps the file in your working folder. Check that .cube/allowed_signers lists only keys that you trust, then run cube trust init, which commits it signed with your key.

The trust root pin is not tamper-proof

Section titled “The trust root pin is not tamper-proof”

This is a warning, not a refusal. The pin is in your global git config, which an agent that runs as your account can change. On a machine where only you commit, you can accept it. On a server that several accounts share, root pins the trust root in the system config instead (see signed acts).

A human-only act is not signed

Section titled “A human-only act is not signed”

pre-push, in a knowledge base that asks for signed acts:

A rule change, the clearing of a bypass and a change to the code that judges commits count only on a commit signed by a key that .cube/allowed_signers lists. HUMAN_ONLY_BY_AGENT is an ERROR, and pre-push refuses the push. Instead of it is not signed, the message can end with another reason:

For a change to the code that judges commits, the message adds and no signed merge on the pushed ref's first-parent line brings it in.

What to do: a person makes the act in a commit of their own, signed with git commit -S by a listed key. A change to the code that judges commits can also come in through a merge that a listed key signs (git merge --no-ff -S BRANCH). Make the trust root before such acts: an act whose first parent comes before the trust root does not count. See signed acts.

commit-msg prints the same code when it accepts such a commit in a knowledge base that asks for signed acts, because git signs a commit only after its hooks run:

The commit is made. Sign it if a person made the act; pre-push checks the signature.

The bypass scan of every pre-commit and pre-push run lists the same code for the commits since adoption:

This list never blocks a commit, and it never blocks a push for a commit that is already on the remote. An act made before the trust root stays in it.

ssh-keygen is not found

Section titled “ssh-keygen is not found”

pre-push checks signatures with OpenSSH’s ssh-keygen, and looks for it only in /usr/local/bin, /usr/bin and /bin. Install the OpenSSH client from your system’s packages. Like every program that the hooks run, it must pass the ownership check (see a program is not safe to run).
