Signed acts

No. 015

Some acts belong to a person, never to an AI agent. From 0.3.0 on Linux, and from 0.4.0 on macOS, a knowledge base can ask that the git hooks count such an act only on a commit that a person signed with an SSH key that the knowledge base trusts. Signing is opt-in: one guided command, cube trust init, sets it up.

Opt in

Section titled “Opt in”

A knowledge base asks for signed acts when one of these is true:

  • a trust root is pinned in protected git config: cube.trustRoot and cube.trustKey, in the system config or in your global config;
  • the first parent of the commit holds .cube/allowed_signers.

Until then, an act that would need a signature passes without one. The git hooks list it as HUMAN_ONLY_BY_AGENT, a WARN that blocks nothing, and add one hint line:

Once a knowledge base asks for signed acts, the rules on this page apply, and they fail closed: an act without a signature that counts is HUMAN_ONLY_BY_AGENT, an ERROR, and pre-push refuses the push. A half setup fails the same way: a .cube/allowed_signers with no pin, or a pin that does not count. To opt out again, you must remove .cube/allowed_signers, and that change is itself an act that needs a signature. A gate repository always asks for signed acts.

One commit needs a signature in every knowledge base: the commit that adds .cube/allowed_signers, which opts the knowledge base in. It counts only when a key that its own .cube/allowed_signers lists signed it, so pre-push refuses it otherwise. An AI agent therefore cannot opt a knowledge base in with a list that names its own key. cube trust init makes such a commit.

Which acts need a signature

Section titled “Which acts need a signature”
  • A rule change: a commit with a Cube-Act: v=1 act=rule-change ... trailer, for example to keep a change that weakens the kit’s rules or removes a pack.
  • The clearing of a bypass: a commit with a Cube-Act: v=1 act=clear-bypass ... trailer.
  • A change to the code that judges commits: the kit’s tools (_kit/tools/ in the starter kit) and everything in .cube/: the settings, the kit lock, the hook scripts and .cube/allowed_signers itself.
  • An adoption commit that you push, unless it is the first commit of the repository. cube adopt writes .cube/, so its commit is a setup commit.

Each of these counts only on a commit signed by a key that .cube/allowed_signers lists, as that file stands in the commit’s first parent. A change to the code that judges commits, and an adoption commit, also count when a merge that a listed key signed brings them in. Every other commit needs no signature.

What you need

Section titled “What you need”
  • git 2.34 or later, which signs commits with SSH keys.
  • ssh-keygen (from OpenSSH) in /usr/local/bin, /usr/bin or /bin (on macOS also /opt/homebrew/bin). The git hooks and cube trust init run it only when it passes the same ownership check as every program the hooks run (see the programs the hooks run).
  • Linux or macOS. On Windows, ssh-keygen is not on the search path that cube gives its programs, so in a knowledge base that opted in, pre-push on Windows cannot check a signature and refuses a push that holds such an act: push those commits from Linux or macOS.

Set up the trust root

Section titled “Set up the trust root”

The owner of the knowledge base does this once, on the owner’s own machine, in the top folder of a clone of the knowledge base:

It shows each step and asks before each change. --yes answers yes to every question, for scripts (not when you join and must type a fingerprint, see Teams). Before it changes anything, it refuses outside a git repository, when the index holds staged changes, and when the adoption commit is not on the remote yet (push first: see below). Run it again at any time: a step that is done says so and asks nothing.

What it does, step by step:

  1. Your SSH key. It uses --key FILE, a public key file (.pub), or else the first of ~/.ssh/id_ed25519.pub, ~/.ssh/id_ecdsa.pub and ~/.ssh/id_ed25519_sk.pub. It never reads a private key. With no key, it offers to make ~/.ssh/id_ed25519 with ssh-keygen, which asks for the passphrase itself: give one. That needs a terminal. A FIDO security key, which signs only when you touch it, is safer still: make it yourself (ssh-keygen -t ed25519-sk) and pass it with --key.
  2. Signing in this clone only. It sets gpg.format and user.signingkey in the clone’s own config. It never sets commit.gpgSign and never writes your global config, so an AI agent that commits in the same clone never signs. You sign each act yourself.
  3. The trust root. It writes .cube/allowed_signers with a line for your key and commits it with git commit -S. That commit is the trust root. It checks the signature with git verify-commit. The key’s name in the file is the role owner; give --principal ROLE for another role. It is never a person’s name or email address, because the file is committed. An existing .cube/allowed_signers that is not committed yet is kept, and your key is added when it is missing. When your last commit holds a .cube/allowed_signers, the knowledge base opted in already, and cube trust init joins it instead, also when the file lists your key (see Teams). So if you stop after this step, the next run joins your own trust root: type the last 8 characters of your own key’s fingerprint.
  4. The pin. It writes cube.trustRoot (the commit) and cube.trustKey (your key’s fingerprint) into your global git config, and warns that a pin there is not tamper-proof: an agent that runs as your account can change your global git config. Run as root, it writes them into the system config, which only root can write.
  5. What changed, and how to undo it.

Push before you run it. An act in a commit that comes before the trust root counts no more once the knowledge base asks for signed acts, so pre-push refuses such a commit if it is not on the remote yet. In a new knowledge base, that is the adoption commit: push it first, while it passes with a WARN. Then run cube trust init, and your next push takes the trust root along.

Teams

Section titled “Teams”

Signing is opt-in for the whole knowledge base, not for one person. When one person runs cube trust init and pushes, every clone gets .cube/allowed_signers, and every clone then asks for signed acts. So one person’s start opts in the whole knowledge base: agree as a team first.

  1. Agree first. Decide together that the knowledge base uses signed acts, and who starts.

  2. One person starts. That person runs cube trust init as above and pushes. They give each other person the fingerprint of their key (cube.trustKey in what cube trust init prints), by chat or in person.

  3. Each other person joins. After a pull, run cube trust init in your own clone. It finds .cube/allowed_signers in your last commit, so it joins the knowledge base’s signers instead of making a trust root, and it writes and commits nothing in the knowledge base. It shows the commit that opted in (the commit that added the file): its id, author, date, and the fingerprint of the key that signed it. It refuses to join when a key that the commit’s own .cube/allowed_signers lists did not sign it, and when a later change of the signer files is not signed by a key listed before it, as pre-push checks them. An AI agent could have written the list, so compare the fingerprint with the person who started, by chat or in person. Then type the last 8 characters of the fingerprint as that person gave them. Anything else is a no, and nothing changes. While you must type it, a join needs a terminal, and --yes is refused: a person must type the answer.

  4. The join pins that commit as your trust root (in your global git config, or in the system config as root), sets up signing in your clone (step 2 above), and prints one line with your key. It asks which role names your key: member when you type nothing (and with --yes), or the role that --principal ROLE gives. When the file lists your key already, there is no line: your signed acts count at once.

  5. Send that line to a trusted signer: a person whose key .cube/allowed_signers lists already.

  6. A trusted signer adds it to .cube/allowed_signers in a commit that they sign, and pushes:

    After you pull that commit, your own signed acts count.

Until you join, pre-push refuses every act that needs a signature in your clone, and names the commit that opted in (see troubleshooting).

On a server that several accounts share, root pins the trust root once, in the system config, for every account: root runs cube trust init in a clone, or pins by hand (see pin the trust root). Each other account then runs cube trust init. Root vouched for the fingerprint, so it asks for none and pins nothing: it sets up signing in the account’s clone and prints the key line. When root’s pin names another commit, an account that is not root cannot replace it, and cube trust init refuses, naming both.

What cube trust init does, by hand

Section titled “What cube trust init does, by hand”

You can make the same setup without cube trust init, or with your own choices at each step. In the commands, replace these words with your own values:

  • KEYFILE: the full path of the key file, for example a file in the .ssh folder of your home folder.
  • FINGERPRINT: the fingerprint of the key, from step 1.
  • COMMIT: the commit id of the trust root, from step 3.
  • BRANCH: the name of a branch that you merge.

3. Commit .cube/allowed_signers, signed

Section titled “3. Commit .cube/allowed_signers, signed”

Write the file .cube/allowed_signers with an editor, in git’s format: one line for each key. A line holds a name for the key, such as owner (a role, not a person’s name), then namespaces="git", then the key type and the key from KEYFILE.pub:

Commit the file, signed. This commit is the trust root. Check its signature: git must print Good "git" signature for owner with your fingerprint. The last command prints the commit id.

A signed act counts only when its first parent comes after the trust root. So make the trust root before the first act that needs a signature, or push the earlier acts first.

4. Pin the trust root

Section titled “4. Pin the trust root”

The pin is two values in protected git config: the commit id of the trust root and the fingerprint of the owner’s key. Both values must be in the same config. With .cube/allowed_signers committed but no pin, pre-push refuses every act that needs a signature.

On your own machine, where only your account commits, pin it in your global git config:

pre-push then warns that the pin is not tamper-proof: an agent that runs as your account can change your global git config.

On a server that several accounts share, root pins it in the system config, which only root can write. As root, first check that the clone on the server has the trust root and that your key signed it. In these commands, KB is the full path of the clone on the server.

Teams with a shared server can also send every push through a gate repository: a bare repository that belongs to an account of its own. Its pre-receive hook, cube hook pre-receive, runs the same checks as pre-push and reads the same pin from the system config, so no account that commits can skip or change them.

5. A new knowledge base: a signed adoption commit

Section titled “5. A new knowledge base: a signed adoption commit”

Instead of pushing the adoption commit before the trust root, you can make the trust root right after the first commit, before cube adopt, and sign the adoption commit. cube adopt makes its commit with git, so after step 4 let git sign that one commit: turn signing on right before cube adopt, and off again right after it, so that an AI agent that commits in the same clone never signs. The adoption commit then sits on your branch, signed; the history stays linear, and the git hooks report no bypass. The last command must print Good "git" signature for owner.

If git cannot sign, cube adopt stops with git commit ... failed and leaves its files staged: unstage them with git reset --quiet, make the key usable, run cube adopt again, and then turn signing off.

A knowledge base whose adoption commit you pushed with an earlier release needs nothing here: pre-push judges only the commits that it pushes.

Sign an act

Section titled “Sign an act”

  • A rule change or the clearing of a bypass: make the commit with its Cube-Act trailer (see hooks and the ratchet), and sign it: git commit -S. Such an act counts only on a signed commit of its own.

  • A change to the code that judges commits: sign the commit, or let an agent commit the change on a branch, review the branch, and merge it with a signed merge:

    The merge brings in the changes to the code that judges commits.

More keys

Section titled “More keys”

A commit signed by a key that .cube/allowed_signers already lists can add a key: add a line for the new key, and commit the file with git commit -S. The new key counts from the next commit.

Retire a key

Section titled “Retire a key”

Make one signed commit that removes the key’s line from .cube/allowed_signers and adds the key to .cube/revoked_signers. That file is in git’s format for revoked keys: one line for each key, the key type and the key, with no name. Never remove a line from it. pre-push refuses a key that the first parent’s, the pushed tip’s or the remote tip’s .cube/revoked_signers lists. The signatures that the key made before still count.

A new trust root

Section titled “A new trust root”

If the owner’s key changes for good, commit a new .cube/allowed_signers that lists the new key, signed with the new key. Before you push that commit, pin it again: set cube.trustRoot to the new commit and cube.trustKey to the new fingerprint, in the same config as before. The checks then start from the new trust root.

What the hooks check

Section titled “What the hooks check”

In a knowledge base that asks for signed acts:

  • pre-push checks each act that needs a signature, in the commits that it pushes. The signature must be good, by a key in .cube/allowed_signers as git holds it in the commit’s first parent, never as your working folder holds it. The first parent must come after the trust root, and each change of .cube/allowed_signers or .cube/revoked_signers since the trust root must be signed by a key that was listed before it. A key that .cube/revoked_signers lists does not count. An act that fails is HUMAN_ONLY_BY_AGENT, an ERROR, and pre-push refuses the push.
  • commit-msg cannot see a signature, because git signs a commit only after its hooks run. It lists each act with HUMAN_ONLY_BY_AGENT and says that pre-push checks the signature. The commit is made.
  • The bypass scan of every pre-commit and pre-push run checks the same signatures in the commits since adoption. It lists what it finds and never blocks a commit. An act that you made before the trust root stays in that list. A cleared bypass counts only when the clearing act’s signature counts.
  • The gate repository, on a shared server, checks the same for every push that it receives, and refuses the whole push when one commit fails.

In a knowledge base that does not ask for them, the same hooks list each such act as a WARN with the hint above, and a clearing act clears its bypass without a signature.

On a machine where only your account commits, these checks run in your own clone, so an agent that runs as your account could change them. A gate repository on a shared server closes that gap. The messages and what to do about them are in troubleshooting.
