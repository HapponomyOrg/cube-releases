Upgrade

No. 010

There are two ways to upgrade The Cube. Both install the newest release of the channel, and both check it before anything changes:

  • From 0.4.0 on every system, and on Linux from 0.3.0: run cube self update.
  • On every system: run the install command again. It is the way from 0.3.0 to 0.4.0 on macOS and Windows, where the cube self update of 0.3.0 refuses, and from 0.2.0, which has no cube self update.

cube self update

Section titled “cube self update”

From 0.4.0 on every system, and on Linux from 0.3.0:

It changes nothing until every check passes:

  1. The signature. The channel manifest must be signed by one of Happonomy’s two keys, which are built into cube. It must not have expired, and its serial must be no lower than the highest that cube saw before. When Happonomy has revoked its CI key, only a manifest that the backup key signed counts.
  2. GitHub’s record. GitHub’s API must mark the release immutable, and GitHub’s SHA-256 digest of the archive must equal the manifest’s.
  3. The download. The SHA-256 of the downloaded archive must equal the manifest’s.

So cube self update needs no minisign program. It uses HTTPS with your system’s certificate store and the proxy variables; see the network. It reads the alpha channel, the installer’s default, unless you name another with --channel.

It updates only an install that the installer made for your account. It refuses a copy that cargo install made, a cube that another account owns (such as one that root installed), and a cube that is not in the installer’s folders. When the newest release is the version you have, or an older one, it changes nothing: it never installs an older version.

On Windows, the update moves the current junction to the new version, as the installer does, and unpacks the download with the tar.exe in Windows’ system folder. On macOS and Windows, the cube self update of 0.3.0 refuses with exit 3 and changes nothing: run the install command once to get 0.5.1.

Hearing about a new release

Section titled “Hearing about a new release”

The explorer checks once a day for a newer release (from 0.4.0 on every system, and on Linux from 0.3.0) and shows a badge in its title bar when there is one. It sends no identifier, and you can turn it off; see privacy. The releases page on GitHub lists every release; to hear about a new one on any system, watch the repository’s releases on GitHub.

What an upgrade does

Section titled “What an upgrade does”

The installer and cube self update do the same:

  • They install the new version into a folder of its own, beside the version you have.
  • When every check passes, they switch the commands to the new version in one step. A cube that runs keeps running. An upgrade cut short leaves the version you had.
  • They keep the version you had before. Older versions are removed.
  • They do not touch your knowledge bases, your settings in ~/.cube/config.toml or the git settings that cube setup wrote.

Then cube --version prints the new version. Where it installs shows the folders.

After the upgrade, in each knowledge base

Section titled “After the upgrade, in each knowledge base”
  1. Run cube check. If it reports SKILL_STALE, write the agent skill again with cube skill render --install, and commit it.
  2. Run cube doctor. Its cube-path and cube-versions items show that the git hooks run the new version. The hooks need no new cube setup: cube setup records the command link (for example ~/.local/bin/cube), and the upgrade points that link at the new version.

The formats

Section titled “The formats”

A release that changes the format of a knowledge base or a kit says so in its release notes. Every release so far keeps cube_format 1 and kit_schema 1, so your knowledge bases need nothing to move. An upgrade never raises the format of a knowledge base. See versioning and compatibility.

Skipped releases

Section titled “Skipped releases”

The installer and cube self update always install the newest release, so you can skip releases. Read the notes below for each release that you skipped, oldest first.

Going back

Section titled “Going back”

cube self rollback (from 0.4.0 on every system, and on Linux from 0.3.0) makes the version kept before current again, by the same one-step switch. It fetches nothing, and it keeps the version it leaves, so cube self update can return to it.

The installer installs only the newest release of the channel. The version that it keeps is there so that an upgrade cut short leaves a cube that works.

Notes for each release

Section titled “Notes for each release”

From 0.2.0 to 0.5.1

Section titled “From 0.2.0 to 0.5.1”

0.3.0, 0.4.0 and 0.5.0 were tagged but never published, so 0.5.1 is the release after 0.2.0. Its steps hold every step of the two sections below it.

  • Run the installer this time. 0.2.0 has no cube self update, so use the install command above, on every system. From 0.5.1 on, cube self update does the next upgrade on every system.
  • macOS and Windows may wait. A release is published when its Linux tests pass. When 0.5.1 has no build for your system, the installer installs nothing and prints the command for the newest earlier release that has one (with CUBE_VERSION); you can keep 0.2.0 and run the installer again for a later release. See troubleshooting.
  • Turn the hooks on (macOS and Windows). The git hooks, cube setup and cube doctor now work there. In each knowledge base, run cube setup, then cube doctor. On Windows, first install Git for Windows for every account, and give cube setup the Python of the kit’s checks: cube setup --python <path to python.exe> or cube setup --venv <folder>.
  • Windows: write the hook shims again. Git for Windows 2.56 moved its own git.exe from mingw64\bin to ucrt64\bin, and the hook shims that an earlier cube wrote into .cube/hooks/ do not look there, so every hook stops. cube setup does not change the shims: run cube adopt once in each knowledge base, which writes them again and commits them, then cube setup again.
  • The update check. The explorer now checks once a day for a newer release. The first check tells you so once. To turn it off, set check = false under [update] in ~/.cube/config.toml, or set CUBE_NO_UPDATE_NOTIFIER. See privacy.
  • Signed acts. A knowledge base can now ask that a rule change, the clearing of a bypass, a change to the code that judges commits and a pushed adoption commit count only on a signed commit. It is opt-in: until you run cube trust init in a knowledge base, nothing changes for your pushes. See signed acts.
  • Kits from other people. trusted_keys in .cube/cube.toml is retired: cube doctor warns about it and cube ignores it. Adopt such a kit again with cube adopt --kit <bundle>, which shows what it brings and pins your choice. See kits and packs.
  • Your knowledge bases need nothing. 0.5.1 keeps cube_format 1 and kit_schema 1.
  • The agent skill. Run cube check in each knowledge base. If it reports SKILL_STALE, run cube skill render --install and commit the skill.

What is new in 0.5.1: the release notes.

From 0.3.0 to 0.4.0

Section titled “From 0.3.0 to 0.4.0”
  • On Linux, run cube self update. On macOS and Windows, run the install command this time: the cube self update of 0.3.0 refuses there. From 0.4.0 on, cube self update does the next upgrade on every system.
  • Turn the hooks on (macOS and Windows). The git hooks, cube setup and cube doctor now work there. In each knowledge base, run cube setup, then cube doctor. On Windows, first install Git for Windows for every account (the hooks read protected git config with its own git.exe under Program Files), and give cube setup the Python of the kit’s checks: cube setup --python <path to python.exe> or cube setup --venv <folder>. Until it records one, cube check on Windows stops before the kit’s checks.
  • The update check. On macOS and Windows, the explorer now checks once a day for a newer release, as on Linux. The first check tells you so once. To turn it off, set check = false under [update] in ~/.cube/config.toml, or set CUBE_NO_UPDATE_NOTIFIER. See privacy.
  • cube doctor does more. It judges the git, gh and python3 that cube setup recorded, warns about risky git settings and an old git, reports your editor, terminal and worktrees, and removes the hooks’ stale cube-* folders. cube doctor --inventory lists your MCP servers, plugins and connectors by name only.
  • Your knowledge bases need nothing. 0.4.0 keeps cube_format 1 and kit_schema 1.
  • The agent skill. Run cube check in each knowledge base. If it reports SKILL_STALE, run cube skill render --install and commit the skill.

From 0.2.0 to 0.3.0

Section titled “From 0.2.0 to 0.3.0”
  • Run the installer this time. 0.2.0 has no cube self update, so use the install command above, on every system. From 0.3.0 on, on Linux, cube self update does the next upgrade.
  • The update check. On Linux, the explorer now checks once a day for a newer release. The first check tells you so once. To turn it off, set check = false under [update] in ~/.cube/config.toml, or set CUBE_NO_UPDATE_NOTIFIER. See privacy.
  • Signed acts. On Linux, a knowledge base can now ask that a rule change, the clearing of a bypass, a change to the code that judges commits and a pushed adoption commit count only on a commit signed with a key that .cube/allowed_signers lists. It is opt-in: until you run cube trust init in a knowledge base, the hooks list such an act as a warning with a hint, and pre-push lets it through. See signed acts.
  • Your knowledge bases need nothing. 0.3.0 keeps cube_format 1 and kit_schema 1.
  • The agent skill. Run cube check in each knowledge base. If it reports SKILL_STALE, run cube skill render --install and commit the skill.

From 0.1.0 to 0.2.0

Section titled “From 0.1.0 to 0.2.0”

  • The install moves. The first run of the 0.2.0 installer moves the 0.1.0 programs into the layout with one folder per version, and keeps 0.1.0 as the previous version:

    System 0.1.0 was in 0.1.0 is now in
    Linux and macOS ~/.local/bin ~/.local/share/cube/versions/0.1.0; ~/.local/bin holds links
    Windows %LOCALAPPDATA%\Programs\cube %LOCALAPPDATA%\Programs\cube\versions\0.1.0

  • Windows: open a new terminal. Your user PATH now names %LOCALAPPDATA%\Programs\cube\current instead of %LOCALAPPDATA%\Programs\cube. A terminal that was open before the upgrade does not see the change.

  • Your knowledge bases need nothing. 0.2.0 keeps cube_format 1 and kit_schema 1.

  • The agent skill. Run cube check in each knowledge base. If it reports SKILL_STALE, run cube skill render --install and commit the skill.

  • The opt-in for a per-user cube. If you listed ~/.local/bin/cube in cube.allowUserOwned, the entry stays valid: that path is now the link into the version folder, and the hooks follow that one link. On Linux, cube doctor shows how the hooks judge it.
